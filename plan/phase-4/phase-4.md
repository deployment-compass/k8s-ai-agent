# Phase 4 — Introduce the LLM

## 1. Phase objective

At the end of Phase 4, you should be able to do this:

```text
HTTP Request
     │
     ▼
  FastAPI
     │
     ▼
 ChatService
     │
     ▼
 BaseLLMClient
     │
     ▼
 LLM Provider API
     │
     ▼
Structured Response
```

For example:

```http
POST /api/v1/chat
{ "message": "What does CrashLoopBackOff mean?" }
```

and receive a structured, evidence-free (for now) explanation generated by an LLM.

The important part is that **the API layer should not contain any LLM SDK code**, exactly like the Kubernetes SDK is hidden behind `KubernetesClient`.

Phase 4 connects the LLM **without Kubernetes tools**. Tool calling is Phase 5.

| Decision | Choice | Reason |

| Provider | **OpenRouter** (default), swappable | Free models available, OpenAI-compatible API |

# 3. Free model landscape (as of August 2026)

All recommended free options speak the **OpenAI-compatible chat completions API**.
That is the key insight that makes one adapter cover everything.

| Provider | Example model ID | Free limits | Base URL |
| --- | --- | --- | --- |
| **OpenRouter** (default) | `deepseek/deepseek-r1:free`, `meta-llama/llama-3.3-70b-instruct:free` | 20 req/min; 50 req/day (1000/day after a one-time $10 credit) | `https://openrouter.ai/api/v1` |
| Groq | `llama-3.3-70b-versatile` | Generous free tier, very fast inference | `https://api.groq.com/openai/v1` |
| Google Gemini | `gemini-2.5-flash` (AI Studio key) | Solid free tier | `https://generativelanguage.googleapis.com/v1beta/openai/` |
| Ollama (local) | `llama3.1`, `qwen2.5` | Unlimited, offline, no key | `http://localhost:11434/v1` |

### Warnings worth internalizing

- The free roster on OpenRouter **rotates monthly**. Model IDs that worked last month may be gone. Never hardcode a model ID in code — always configure it.
- DeepSeek/Gemini/Mistral *direct* free IDs on OpenRouter come and go. Check `openrouter.ai/models` with the `:free` filter before relying on one.
- `openrouter/free` is an auto-router that picks any currently-available free model. Useful as a fallback, less predictable for structured output testing.
- Free tiers are fine for development and learning, not for production traffic.

# 4. Design pattern: Ports & Adapters

We apply the same principle that made `KubernetesClient` work:

> **The rest of the application depends on your own interface, not on a vendor SDK.**

```text
                ┌─────────────────────┐
                │    ChatService      │
                └──────────┬──────────┘
                           │ depends on
                           ▼
                ┌─────────────────────┐
                │   BaseLLMClient     │   ← the "port" (ABC)
                └──────────┬──────────┘
                           │ implemented by
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
┌──────────────────┐ ┌────────────┐ ┌──────────────┐
│ OpenAICompatible │ │ MockLLM    │ │ (future:     │
│ Client           │ │ Client     │ │  Anthropic…) │
└────────┬─────────┘ └────────────┘ └──────────────┘
         │
         ▼
   openai SDK (AsyncOpenAI)
         │
         ▼
   OpenRouter / Groq / Gemini / Ollama / OpenAI
```

### Why this works so well here

Every provider in the table above is OpenAI-compatible. So:

```text
One adapter (OpenAICompatibleClient)
        +
configurable base_url + api_key + model
        =
all providers, selected by environment variables
```

Swapping OpenRouter for Groq or local Ollama becomes:

```text
LLM_PROVIDER=openrouter   →   LLM_PROVIDER=groq
```

No code changes. That is the whole point of the pattern.

### Why a Mock client too

`MockLLMClient` returns deterministic structured responses. It gives us:

- Tests that run offline and cost nothing
- A way to develop Phase 5 tool calling without burning rate limits
- A safe default when no API key is configured (`LLM_PROVIDER=mock`)

# 6. Configuration

Extend `Settings` in `app/config.py`:

```python
llm_provider: str = "mock"          # mock | openrouter | groq | gemini | ollama | openai
llm_api_key: str = ""               # empty is valid for mock/ollama
llm_base_url: str = ""              # derived from provider when empty
llm_model: str = ""                 # derived from provider when empty
llm_timeout_seconds: float = 30.0
llm_temperature: float = 0.2
llm_max_retries: int = 2
```

Provider presets live in the factory, not scattered around:

```text
openrouter → https://openrouter.ai/api/v1
groq       → https://api.groq.com/openai/v1
gemini     → https://generativelanguage.googleapis.com/v1beta/openai/
ollama     → http://localhost:11434/v1
openai     → https://api.openai.com/v1
mock       → (no network)
```

Explicit env vars always override presets. Default model suggestions per provider:

```text
openrouter → deepseek/deepseek-r1:free
groq       → llama-3.3-70b-versatile
gemini     → gemini-2.5-flash
ollama     → llama3.1
```

`.env.example` gains:

```text
LLM_PROVIDER=openrouter
LLM_API_KEY=
LLM_MODEL=deepseek/deepseek-r1:free
```

Security note: the API key lives only in `.env` (gitignored). It must never appear in logs or error messages.

# 7. Structured output

## 7.1 The contract

`ChatResponse` evolves from `{response: str}` to:

```json
{
  "answer": "CrashLoopBackOff means ...",
  "reasoning_summary": "Identified the question as a concept explanation...",
  "suggested_next_steps": [
    "Check pod events with GET /clusters/default/namespaces/{ns}/events"
  ]
}
```

Why three fields?

- `answer` — what the user reads
- `reasoning_summary` — forces the model to expose its thinking briefly; becomes the seed of `agent_reasoning_summary` in the audit log (Phase 10)
- `suggested_next_steps` — nudges the model toward the diagnostic workflow we formalize in Phase 5/6

## 7.2 How to get valid JSON reliably

Not all free models support native `response_format={"type": "json_schema"}`.
So the baseline approach is deliberately boring:

```text
System prompt demands strict JSON matching the schema
        ↓
Model returns text
        ↓
Parse with Pydantic (validate + coerce)
        ↓
 ┌──────┴───────┐
Valid         Invalid
 │               │
 ▼               ▼
Return      One retry with error feedback appended
                │
           ┌────┴────┐
          Valid    Invalid
           │         │
           ▼         ▼
         Return   raise LLMParseError → HTTP 502
```

If a provider turns out to support JSON mode well (OpenRouter routes many models that do), we can opt into `response_format={"type": "json_object"}` later as an optimization. Correctness first, optimization second.

## 7.3 The system prompt

Lives in `llm/prompts.py`, roughly:

```text
You are a Kubernetes operations assistant...
- Answer questions about Kubernetes concepts, troubleshooting, and operations.
- You currently CANNOT inspect clusters. If asked about a specific cluster,
  explain what you would inspect and suggest next steps.
- Respond ONLY with a JSON object matching:
  { "answer": string, "reasoning_summary": string,
    "suggested_next_steps": string[] }
- No markdown fences. No text outside the JSON.
```

The "you cannot inspect clusters yet" clause matters: it sets user expectations correctly during Phase 4 and gets replaced by tools in Phase 5.

# 8. Error handling

Map provider failures to meaningful HTTP responses instead of tracebacks:

```text
Invalid API key / auth failure        → 500 (config problem, log details server-side)
Rate limited (429)                    → 429 with Retry-After if provided
Timeout                               → 504 Gateway Timeout
Provider unavailable / 5xx            → 502 Bad Gateway
Malformed JSON after retry            → 502 with "model returned invalid output"
Empty message                         → 422 (Pydantic constraint on ChatRequest)
```

Principles:

- The `openai` SDK raises typed exceptions (`AuthenticationError`, `RateLimitError`, `APITimeoutError`, `APIConnectionError`). Catch them in the adapter, translate to our own exception types (`app/llm/exceptions.py` or inline in `base.py`), map to HTTP in the service/API layer.
- Never include the API key, full request headers, or raw provider payloads in error responses.
- Log enough to debug (provider, model, status code, latency) without leaking secrets.

# 9. Testing strategy

Same layered philosophy as Phase 2:

### Level 1 — Unit: factory

```text
settings.llm_provider = "openrouter" → OpenAICompatibleClient with correct base_url
settings.llm_provider = "mock"       → MockLLMClient
unknown provider                     → clear error
```

### Level 2 — Unit: adapters

```text
MockLLMClient returns valid structured response
OpenAICompatibleClient translates SDK exceptions into our exception types
(mock the AsyncOpenAI client — no network in tests)
```

### Level 3 — Unit: parsing

```text
valid JSON            → parsed ChatResponse
JSON in markdown fences → parsed (tolerant extraction)
invalid JSON twice    → LLMParseError
missing required field → retry path taken
```

### Level 4 — Integration: endpoint

```text
POST /chat with mocked client → 200 structured body
provider error mapped to correct HTTP status
existing 13 tests stay green (3 chat tests updated for new schema)
```

# 10. What we explicitly DON'T do

### No tools

The LLM cannot touch Kubernetes in Phase 4. `KubernetesClient` exists, but nothing wires it to the model. That's Phase 5.

```text
FastAPI → LLM
not:
FastAPI → LLM → Kubernetes
```

### No conversation history

Single request → single response. No session state, no storage. Phase 6 introduces `AgentState`.

### No streaming

Plain JSON request/response. SSE can be added later behind a new endpoint without breaking this one.

### No LangGraph

A plain async function call chain is enough. Introduce workflow frameworks when there's a workflow (Phase 6).

### No hardcoded provider logic outside the adapter

If you find yourself writing `if provider == "groq"` anywhere except `factory.py`, stop and refactor.

# 12. Key architectural decisions recap

### Approach A — One generic adapter vs. one adapter per provider

```text
A: OpenAICompatibleClient(base_url, api_key, model)
B: OpenRouterClient, GroqClient, GeminiClient, OllamaClient…
```

**Approach A.** Every target speaks the same protocol; B would be four copies of nearly identical code. Add a dedicated adapter only when a provider genuinely diverges (e.g., native Anthropic Messages API).

### Prompt-based JSON vs. native structured outputs

Prompt + Pydantic validation + retry. Works everywhere including models without JSON mode; upgrade selectively later.

### Where does the system prompt live?

`llm/prompts.py`, versioned in git like code. Prompts are part of the product; treat them seriously.
